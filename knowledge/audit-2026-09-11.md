# SubSync audit — 2026-09-11

Version audited: **2.0.9.0** (released artifact, commit `2969850`), installed into a private test
server. Everything below was reproduced against a live Jellyfin 12 + this plugin; nothing is a guess
from reading code alone unless it is explicitly marked *static* or *unverified*.

**Goal of this document: list what is wrong, for later patching. No fixes were made.**

## 1. How it was tested, and what that does and does not cover

| What | How |
|---|---|
| Own Jellyfin 12 server at `127.0.0.1:8096`, admin user `admin`, plugin installed from the released zip | local, disposable — the user's server was not used |
| Media | real episode (`Helikopterrånet`/The Helicopter Heist S01E01, 2.38 GB, 50 subtitle tracks, same file as the user's server) hardlinked into a Movies library and a Shows library (series + 2 episodes) |
| Server API | every `/SubSync/*` endpoint called directly with curl/python, happy path **and** edge cases (bad ids, missing bodies, out-of-range indexes, duplicates, unknown ids, no auth) |
| GUI | the plugin's real served pages (`/web/configurationpage?name=SubSync`, `/web/configurationpage?name=subsync-main`) rendered in jsdom with Jellyfin Web's `ApiClient`/`Dashboard` stubbed and `fetch` proxied to the live server, then the actual controls were clicked (save, sync, cancel, clear cache, tab switches) |
| Static | repo inventory, git tracking state, endpoint inventory, and two parallel read-only code audits |

**Limits — read before trusting a GUI claim:**
- No pixels. The browser tool refuses private/local addresses and this host has no desktop, so nothing
  was verified visually: layout, overlap, colour, truncated text and responsive behaviour are untested.
- jsdom has no layout engine, so `getClientRects()` is empty for every element — visibility checks in
  my harness are meaningless.
- Jellyfin Web's real shell was not loaded; its own event plumbing (drawer, page manager) is stubbed.
  Where this could change a conclusion it is flagged *unverified* below.
- Single-user, single-server: permissions, multi-user isolation and concurrent browsers are untested.

### D1 — Kill kills everything, and there is no per-job kill

- Area: API. `SubSyncController.cs`, `[HttpPost("Kill")]` → `_syncService.KillAll()`; it takes **no job id**.
- Evidence (live): `POST /SubSync/Kill {"JobId":"00000000-..."}` → `{"queuedCancelled":0,"runningKilled":2,...}`
  — an unknown id killed two running jobs. A later call with no body returned all zeros (queue already
  empty), and after a 120-task batch the same call returned `{"queuedCancelled":117,"runningKilled":4}`.
- The GUI never calls it (`subsync.js` has no kill/cancel-per-job; the main page only cancels a whole batch),
  so the plugin ships a destructive endpoint that nothing in the product uses, while the thing users
  actually need — stop **this** job — does not exist.
- Fix direction: either drop the endpoint or make it take a job id and kill one job; if a global
  "stop everything" is wanted, expose it in the GUI, label it clearly and confirm before running it.

### D2 — "Installed successfully" with a binary path that does not exist

- Area: API + GUI (`/SubSync/Install`, `/SubSync/InstallationStatus`, config page button).
- Repro: save `FfSubSyncPath = /no/such/binary-xyz` in the GUI (accepted, see D3), then press
  *Install / Update ffsubsync*.
- Evidence: `POST /SubSync/Install` → HTTP 200 `{"message":"ffsubsync installed successfully."}` in 1.3 s,
  and `GET /SubSync/InstallationStatus` immediately after:
  `{"IsInstalled": true, "ManagedBinaryPath": ".../venv/bin/ffsubsync", "ResolvedBinaryPath": "/no/such/binary-xyz", ...}`
  The main page then renders `ffsubsync source: /no/such/binary-xyz` as ordinary status text.
- Impact: the user is told everything is fine and only finds out when a sync fails, with an error that
  points at ffsubsync rather than at their setting.
- Fix direction: `InstallationStatus` should report what will actually be executed, and both the install
  button and the status line should say plainly when that path does not resolve.

### D3 — Settings validation is partial, and silent

Ten saves were driven through the real config page, each typing one hostile value:

| Typed | Stored | Verdict |
|---|---|---|
| `ParallelWorkers = 99` | `64` | clamped (1..64) |
| `ExtractionTimeoutMinutes = 0` / `100000` | `20` / `240` | clamped (1..240) |
| `MaxSubtitleSeconds = abc` | `10` | fell back to default |
| `MaxOffsetSeconds = -5` | `-5` | **stored** |
| `MaxOffsetSeconds = 100000` | `100000` | **stored** |
| `FfSubSyncPath = /no/such/binary-xyz` | same | **stored** |
| `FfmpegPath = /no/such/ffmpeg-xyz` | same | **stored** |
| `OutputEncoding = not-an-encoding` | same | **stored** |
| `SyncLanguages = qq, zz, !!!@#` | `["qq","zz","!!!@#"]` | **stored** |

- Impact: a negative or absurd `--max-offset-seconds`, a typo'd language tag (silently syncs nothing) or a
  broken binary path all look like a successful save. Nothing in the UI ever says a value was rejected or
  adjusted, so a clamped 99 → 64 is invisible too.
- Fix direction: one shared validation path for both GUI surfaces: ranges for the numeric fields, an
  encoding check, a known-language check, and a visible warning (or refusal) instead of a silent 204.

### D4 — Two GUI surfaces, one config, different subsets

- Dashboard config page: 12 fields — ffsubsync path, ffmpeg path, VAD, max offset, max subtitle seconds,
  encoding, golden-section search, sync mode (copy/replace), multi-sync mode, parallel workers, extraction
  timeout, only-sync-these-languages.
- Main page *Settings* tab: 13 controls — VAD, max offset, max subtitle seconds, encoding, multi-sync mode,
  workers, clear cache, language add, golden-section search, **FixFramerate**, sync mode, ffmpeg path,
  ffsubsync path. It has **no** extraction-timeout control; the config page has **no** FixFramerate control.
- The model has 16 keys; `SweepFailStreakLimit`, `SweepMaxItemsPerRun` and `ConfigVersion` are in none of
  the GUIs (sweep limits are only editable by hand).
- Impact: users cannot tell which surface is authoritative, and a setting they set in one place is invisible
  in the other.
- Fix direction: one settings surface (or make both render the same schema), and document the sweep limits.

### D5 — "Workers: 4 in use" when nothing is running

- Area: GUI status line + `InstallationStatus.WorkerSummary`.
- Evidence: with `GET /SubSync/Active` → `{"running":[],"queued":0}`, both the main page status text and the
  status endpoint said `4 in use (setting 4)`.
- Impact: status that overstates activity; the user cannot tell configured from busy.
- Fix direction: report configured vs running separately ("limit 4, 0 running").

### D6 — History tab contradicts itself

- Evidence (`#panel-history` text with one completed batch present):
  `"Sync history Every run on this server... 1 run — shared from the server across every tab/device. Batch 9/11/2026, 9:06:46 PM 3/4 OK Nothing synced yet. Start a sync from the Sync tab and it will show up here."`
- Impact: the empty-state text renders unconditionally, so the page simultaneously says there is one run and
  no runs.
- Fix direction: show the empty state only when the list is empty.

### D7 — Polling is flat out and duplicated

- Evidence: 20 s of an idle main page produced **15 × `GET /SubSync/Batches`** and **13 × `GET /SubSync/Active`**
  (≈1.4 req/s), including three `Batches` calls in a row on load, and each tab click produced another 2-5.
  Every poll pulls the whole batch list with all task details.
- Impact: needless server and network load per open tab; on a slow NAS-backed server this competes with
  extraction for I/O.
- Fix direction: one poller with a short interval while work exists and a slow interval when idle, no polling
  when nothing is running, and (optionally) a lightweight summary endpoint.

### D8 — Batch validation is looser than single sync

- Evidence: `POST /SubSync/Sync {"SubtitleIndex":4}` with a series id → HTTP 400
  `"Item cc1c47b1-...  is not a video."` (correct), while
  `POST /SubSync/Batch {"Tasks":[{"ItemId":"<series id>","SubtitleIndex":1}]}` → **HTTP 200**, batch created.
- Impact: a batch can be created that can never do anything, and its task fails with a generic error.
- Fix direction: validate each task when the batch is created, and reject the whole request with the
  offending task index.

### D9 — No dedupe anywhere in the queue

- Evidence: `POST /SubSync/Sync` for the same item + track index twice → two jobs queued for track 4 of the
  same file. `POST /SubSync/Batch` with three identical tasks → 200; with 120 duplicated tasks → 200 and
  117 queued.
- Impact: totals and ETAs overstate the work; worker slots are spent on repeats (the extraction cache
  softens the cost, but queue bookkeeping — and the user's estimate of how long it takes — is wrong).
- Fix direction: drop tasks already queued/running for the same item + track, and say so in the response.

### D10 — Inconsistent, unhelpful error bodies

- `POST /SubSync/Sync {}` → `"Error processing request."` (no reason). Unknown item id → same. Malformed id →
  `ProblemDetails` with a field error. Out-of-range index → `ProblemDetails`.
- Impact: the GUI can only surface a generic failure for the "no reason" cases, which is exactly what users
  complain about.
- Fix direction: one error shape for the whole controller, always naming the offending value.

### D11 — The resolved mode is opaque

- Evidence: batches created from the same kind of task list came back as `Mode: "normal"`, `"auto"`, then
  `"ultimate"` (120 duplicate tasks → ultimate). Nothing in the response or GUI explains what chose it or what
  changes for the user, yet "ultimate" is the slowest strategy.
- Fix direction: state the resolved mode and why, and let the user pin it.

### D12 — Two versions reported at once

- Evidence: `InstallationStatus` → `"PluginVersion": "2.0.8.0"` while `"PluginIdentity":
  ".../SubSync_2.0.9.0/Jellyfin.Plugin.SubSync.dll"`. (Here the DLL really was an older local build, so this is
  a test artefact — but it shows the number comes from the assembly while the path comes from the manifest, and
  the two can disagree in front of a user.)
- Fix direction: report one version, from the assembly, and say so in the label.

### D13 — (unverified) one press of "Sync selected" may not sync

- Evidence: with the series scope selected, pressing `#ss-syncsel-btn` produced `POST /SubSync/Subtitles/Batch
  {"itemIds":["<series id>"],"expandSeries":true}` — a *preview* fetch — and no batch. No progress or status
  text appeared, and no second press was driven by the harness.
- Needs a human in a real browser: is a second press required, or does the first press fail to create the
  batch? If the former, the button's label promises something it does not do in one click.

### D14 — (unverified) the injected client script injected nothing

- Evidence: `subsync.js` evaluated in a synthetic item-detail page logged `[SubSync] Client script loaded`,
  started polling (`Active`/`Batches`), and added **no** button and made no `/SubSync/Subtitles/{id}` call.
- Caveat: the synthetic DOM is not Jellyfin Web's real item page, so this proves nothing about the real page.
  It should be checked in a real browser with the script installed under Dashboard → General → Custom client
  JavaScript.

### D15 — No authorisation checks anywhere, verified with an unprivileged user

- Area: API. `grep -rn 'IsAdministrator\|RequireAdmin' Api/` → **0 matches**; the controller only carries
  class-level `[Authorize]` (must be logged in as *someone*).
- Method: created a plain user (`audituser`, `IsAdministrator: false`, restricted to one library), logged it
  in, and called the endpoints. Control: Jellyfin's own admin endpoint `GET /Library/VirtualFolders` correctly
  answered **403** for the same token — so the missing checks are the plugin's.

| Call as the ordinary user | Result |
|---|---|
| `GET /SubSync/Jobs` | **200** — full server-wide job history: item ids, track indexes, phases, outcomes, every user's runs |
| `GET /SubSync/Log` | **200** — the whole plugin log, including absolute server paths (`/opt/data/.../Jellyfin.Plugin.SubSync.dll`, config paths) |
| `POST /SubSync/Install` | **200** `{"message":"ffsubsync installed successfully."}` |
| `POST /SubSync/Kill` | **200** — cancelled the job (anyone's queued jobs die, see D1) |
| `GET /SubSync/Subtitles/{hidden series}` | 404 — this one *did* respect library access |

- What install actually runs (so the risk is stated accurately): `python3 -m venv <plugin data>/subsync/venv`,
  then `<venv>/bin/python -m pip install --upgrade pip` and a pip install of ffsubsync. **No `apt-get`
  anywhere in the codebase**, so a delegated report calling this "run apt-get as root" is wrong on that
  detail — but an unprivileged web user can still make the server fetch and install Python packages into the
  plugin's data directory and run ffsubsync.
- Fix direction: gate `/Install`, `/Kill`, `/SpeechCache/Clear` and the log/jobs/history reads on
  `User.IsInRole("Administrator")` (or Jellyfin's admin policy), and decide per endpoint who may read
  server-wide history.

## 7. Delegated static audits (read-only, no code changed)

Two auditors read the source independently of the live testing above. Their reports are reproduced in

### 7.1 Static audit — scheduler and extractor

### Findings — `SubSyncService.cs` + `MkvSubtitleExtractor.cs`

Read-only audit; nothing was modified. Every line number below was read in the file (not inferred), and where I could not prove a failure mode I say so inline.

### 1. Replace mode can destroy the original subtitle with no rollback
- Area: other (write path)
- Where: SubSyncService.cs:3569-3570 (catch/rollback at 3732-3748)
- Severity: critical
- What is wrong: `backupPath` is assigned only *after* `ReplaceExternalSubtitle` returns, but that method is where the original file is overwritten (`File.Copy(temp, original, overwrite: true)`, line 3789). If that copy fails partway — share drops, disk fills, process killed — `backupPath` is still null, so the `catch` block's rollback is skipped and the user's subtitle is left truncated with the `.bak.subsync` sitting on disk unmanaged. The rollback is in fact only reachable for failures *after* a successful replace, i.e. the case that never needs it.
- Evidence: `await ReplaceExternalSubtitle(subtitleStream.Path, tempOutput).ConfigureAwait(false);` / `backupPath = subtitleStream.Path + ".bak.subsync";` (3569-3570).
- Why it matters: in replace mode a network hiccup silently leaves a half-written subtitle in the library and no automatic restore; the user only finds out when the episode plays.
- Direction for a fix: set the backup path before the destructive step (or have the replace routine own the backup+rollback), and treat "copy did not complete" as a rollback trigger rather than a thrown-and-forgotten error.

### 2. Shared extraction pass silently drops cues for tracks with a mixed cue index
- Area: extraction
- Where: MkvSubtitleExtractor.cs:796, 801-819 (consumed at 942-957, cached at SubSyncService.cs:1579/4208)
- Severity: critical
- What is wrong: for an extra (non-primary) track, `needsWalk` is true only when *every* cue point lacks `CueRelativePosition`. In the mixed case (some cue points have the block offset, some do not) the ones without an offset hit `if (reference.RelativePosition < 0) { … continue; }` and are never added to either `walkInCluster` or `byCluster`, so their cues are never read. Unlike a whole track that is skipped, this track is still reported as produced and its truncated SRT is written into the persistent `SubtitleCache`.
- Evidence: `var needsWalk = extraRefs.All(r => r.RelativePosition < 0);` … `if (reference.RelativePosition < 0) { if (needsWalk && …) { … } continue; }`
- Why it matters: a language extracted in a multi-track pass can come out missing lines — a wrong subtitle that looks like a success, and it is cached and reused later.
- Direction for a fix: treat a track as walk-needing if *any* of its cue points lacks an offset, or extract that track alone when the refs are mixed.

### 3. Scheduler touches the media share while holding the queue lock
- Area: scheduler
- Where: SubSyncService.cs:2292-2296 (`ExtractionReady`), which calls `SubtitleCache.TryGet` at 1449 — inside `lock (_queueLock)` opened at 2235
- Severity: high
- What is wrong: `ExtractionReady` is passed as both `canShareMediaFile` and `mayStart`, asked for every candidate on every planning pass (every 750 ms). On a `_extractedReady`/`_extractTried` miss it falls through to `SubtitleCache.TryGet`, which stats the media file (`KeyFor`→`new FileInfo`), `File.Exists`s, reads the whole SRT and calls `File.SetLastAccessTimeUtc`. That is storage IO under the lock the enqueue path waits on — the exact invariant AGENTS.md records (`SpeechIsCached` was memoised for this reason; the enqueue path was measured at 105-424 s per 240 tasks).
- Evidence: `job => ExtractionReady(job),` and `job => ExtractionReady(job) || (!LaneAlive && …)` inside `lock (_queueLock)`; `if (SubtitleCache.TryGet(path, context.Ordinal.ToString(CultureInfo.InvariantCulture), out var text)`.
- Why it matters: queueing a batch stalls behind planning while a slow extraction is running; the batch trickles in and the UI looks like the plugin refuses to parallelise.
- Direction for a fix: answer this predicate from memory only (the lane already publishes readiness), and move any cache probe out of the lock.

### 4. Cue-point parsing does not reset per `CueTrackPositions`
- Area: extraction
- Where: MkvSubtitleExtractor.cs:1810-1857 (`ParseCueRefs`)
- Severity: high
- What is wrong: `clusterPosition`/`relativePosition` are declared once per CuePoint and overwritten by every `CueTrackPositions` child, while `matched` is only a bool. When a cue point carries positions for several tracks, the `CueRef` added for our track carries whichever values the *last* child left behind — potentially another track's cluster. The block then cannot be found there and the cue is lost (or read from the wrong place).
- Evidence: `if (cueTrack == trackNumber) { matched = true; }` … `refs.Add(new CueRef(clusterPosition, relativePosition, cueTime));`
- Why it matters: missing or misplaced lines in the synced subtitle. Note: I could not confirm a multi-track cue point in a real file here — with one `CueTrackPositions` per cue point (the common muxing shape) this is harmless, so treat it as a latent correctness bug, not a proven one.
- Direction for a fix: parse each `CueTrackPositions` into its own local values and add the ref immediately when the track matches.

### 5. `--version` process is spawned synchronously from a property getter, under the queue lock
- Area: scheduler / ffsubsync
- Where: SubSyncService.cs:482 (`BundledFfSubSyncVersion`), called from `EngineIdentity()` (1792) via `SpeechIsCached` (1771, reached from the planner's `JobNeedsHeavyIo` at 2281) and from `engineIdentity` (3200, 3231)
- Severity: high
- What is wrong: the property blocks with `.GetAwaiter().GetResult()` and launches the bundled PyInstaller binary on every uncached evaluation; `RunProcessCaptureAsync` takes no cancellation token and does not register the process in `_liveProcesses`, so it can neither be cancelled nor killed. `BundledFfSubSyncPath` also re-chmods the binary (`File.SetUnixFileMode`) on every read of the property.
- Evidence: `var (exitCode, output) = RunProcessCaptureAsync(path, "--version", null).GetAwaiter().GetResult();` then `EngineIdentity() => string.Join("|", BundledFfSubSyncVersion, …)`.
- Why it matters: a hung or slow binary (cold cache, AV scan, NFS home) freezes the planning pass, the queue, and any API call that waits on that lock — for as long as the process takes; `Kill` cannot reach it.
- Direction for a fix: resolve and cache the version once (behind a token, with the process registered like the others), and never run a process from inside the lock or from a getter.

### 6. A job can stay `Running` forever
- Area: scheduler / logging
- Where: SubSyncService.cs:3026 (`Directory.CreateDirectory(tempDir)`, before the `try` that starts at 3059) and 2407-2432 (`RunSyncJobWithContext`)
- Severity: high
- What is wrong: anything thrown before `RunSyncJob`'s `try` (creating the scratch dir, `video.Path` being null) escapes uncaught; `RunSyncJobWithContext` catches only `OperationCanceledException`, so no terminal status is ever set. The cleanup timer only evicts Completed/Failed/Cancelled jobs, so the job stays `Running` in `_jobs` and in `_runOrder` for the life of the process.
- Evidence: `var tempDir = Path.Combine(Plugin.Instance?.TempPath ?? Path.GetTempPath(), job.Id); Directory.CreateDirectory(tempDir);` (3025-3026).
- Why it matters: the UI shows a job running forever with no error, and history/counters are permanently skewed.
- Direction for a fix: bring the whole body inside the try, and catch `Exception` (not just cancellation) in the wrapper so every path reaches a terminal status.

### 7. `Kill` cannot interrupt a Matroska extraction
- Area: extraction
- Where: SubSyncService.cs:1550 (lane) — `CancellationToken.None`
- Severity: high
- What is wrong: `TryExtractMany`'s `cancellationToken` is documented as "Cancels a long read (Kill in the UI)" and is honoured inside the reader, but the extraction lane always passes `CancellationToken.None`; the lane method itself has no token parameter at all. The job-level kill therefore only takes effect *after* the pass finishes.
- Evidence: `out stats, CancellationToken.None, (ordinal, text) => { … }` inside `TryExtractMany(…)` at 1544-1550.
- Why it matters: "Kill" during the slowest phase (a multi-minute file read) appears to do nothing, and `KillAll`'s process kill has no process to kill because the read is in-process.
- Direction for a fix: give the lane a disposal/kill token (or a shared kill flag) and pass it to `TryExtractMany`.

### 8. A failed ffmpeg extraction is accepted if a partial file exists
- Area: extraction
- Where: SubSyncService.cs:4408-4411
- Severity: high
- What is wrong: the only failure test is `exitCode != 0 && !File.Exists(outputPath)`. If ffmpeg is killed (timeout, OOM) after having created and partially written the output, the non-zero exit is ignored and the truncated SRT is treated as the extracted subtitle; the later "verify" step only checks that the final file is non-empty.
- Evidence: `if (exitCode != 0 && !File.Exists(outputPath)) { throw new InvalidOperationException(...); }`
- Why it matters: a truncated extraction propagates into the sync and can be written to the library (and cached) as a successful result.
- Direction for a fix: fail on any non-zero exit from ffmpeg; sanity-check the extracted SRT (cue count / trailing completeness) before using it.

### 9. Kernel-IO baseline is shared mutable static state raced by parallel lanes
- Area: caching / logging
- Where: MkvSubtitleExtractor.cs:143-144, 601, 1027-1031, 1104-1109
- Severity: medium
- What is wrong: `_kernelBytesAtStart`/`_kernelCallsAtStart` are static, written by `MarkIoBaseline()` at the start of a pass and re-read by `FinaliseStats()` at the end. Up to three lanes (plus job-side passes) extract concurrently, so one pass's baseline is overwritten by another's and the reported delta is arbitrary (often negative). `FinaliseStats` also re-reads the static field instead of the local copy the caller captured at line 601. `/proc/self/io` is process-wide, so even without the race the numbers include ffmpeg/ffsubsync and other lanes.
- Evidence: `if (bytes >= 0 && _kernelBytesAtStart >= 0) { stats.KernelBytesRead = bytes - _kernelBytesAtStart; … }`
- Why it matters: the "kernel N bytes in M calls" figure printed in the extraction line — the number the cost claims rest on — is not trustworthy.
- Direction for a fix: capture the baseline per pass and pass it through to the finaliser (instance state, not statics), and label the figure as process-wide.

### 10. `FinaliseStats` runs before `ReadCalls`/`TotalMs` are assigned
- Area: logging
- Where: MkvSubtitleExtractor.cs:296-301 (and the mirrored block at 310-314)
- Severity: medium
- What is wrong: `FinaliseStats` computes `ReadLatencyMs = ReadMs / ReadCalls`, but `stats.ReadCalls` is assigned on the line *after* the call, and `stats.TotalMs` after that. In the metadata-scan path (no cue refs) `ReadCalls` is never set during the pass, so the summary always reports `0.0 ms/read`. The duplicated comment above both call sites and the misaligned indentation show this was a hand-merged edit.
- Evidence: `FinaliseStats(stats);\n            stats.ReadCalls = reader.ReadCalls;\n            stats.TotalMs = watch.Elapsed.TotalMilliseconds;`
- Why it matters: the ms/read figure — the whole basis of choosing the walk window — reads as zero on exactly the files that needed a walk.
- Direction for a fix: assign `ReadCalls`/`TotalMs` first, then finalise.

### 11. Progress line during a metadata scan always reports 0.0 MB
- Area: logging
- Where: MkvSubtitleExtractor.cs:1483 (with 652-653)
- Severity: medium
- What is wrong: `stats.BytesRead` is only updated inside the cue-refs loop; `ScanClusters` (the no-index path) reports `stats.BytesRead / 1e6` from a counter that is still zero, so every scan line reads `0.0 MB` regardless of what it read.
- Evidence: `progress($"scanning clusters ({visited} read, {stats.BytesRead / 1e6:0.0} MB, {cues.Count} subtitles found)");`
- Why it matters: the user (and the log) sees a stall-looking progress line with no bytes moving on the slowest path.
- Direction for a fix: read the live counter from the reader (`reader.BytesRead`) on the scan path.

### 12. Four planner/cache dictionaries grow without bound
- Area: caching
- Where: SubSyncService.cs:284 (`_extractedReady`), 293 (`_referenceOrdinals`), 299 (`_extractTried`), 1405 (`_speechCachedMemo`); pruning only at 3891-3935
- Severity: medium
- What is wrong: `CleanupOldJobs` trims `_jobs`, `_jobContexts`, `_runOrder` and the refresh gate, but none of these four is ever trimmed or expired — `_speechCachedMemo` is only TTL-checked on read, never removed, and `_referenceOrdinals` is a `GetOrAdd` with no counterpart. Keys are media paths, so the growth tracks the size of the user's library.
- Evidence: `_referenceOrdinals.GetOrAdd(key, ordinals);` and `_speechCachedMemo[path] = (cached, now);` — no removal anywhere.
- Why it matters: a long-lived Jellyfin process accumulates one entry per file ever planned, on top of the job store that is bounded.
- Direction for a fix: prune these alongside the job store (age- or count-bounded).

### 13. Per-reader memory: 4 MB window + up to 384 MB of prefetched ranges
- Area: extraction
- Where: MkvSubtitleExtractor.cs:2537 (`new byte[MaxWindowSize]`), 2238-2240 (`MaxTotalBytes = 384 MB`), 2128-2130 (192 MB), 2572, 2595-2654
- Severity: medium
- What is wrong: every `BlobReader` allocates a fixed 4 MB window regardless of `WindowSize`, and `Prefetch` materialises every range it is given and keeps them in `_ahead` (cleared only at the *start* of the next prefetch, never at the end). The walk budgets 384 MB of ranges in one call. With up to `MaxExtractionLanes = 3` lanes, plus jobs that run their own `TryExtractMany`/`TryExtract` when they miss the cache, peak RSS scales with concurrent readers × ~400 MB.
- Evidence: `private readonly byte[] _window = new byte[MaxWindowSize];` … `const long MaxTotalBytes = 384L * 1024 * 1024;`
- Why it matters: a small container or a NAS with 2 GB can be pushed into swap/OOM by a batch, which then looks like the plugin hanging.
- Direction for a fix: size the window lazily, drop `_ahead` when the pass ends, and make the prefetch budget a function of the lane count / available memory.

### 14. `Dispose` leaves child processes and lanes running
- Area: other (lifecycle)
- Where: SubSyncService.cs:3869-3886
- Severity: medium
- What is wrong: `Dispose` sets `_disposing`, disposes the timer and releases the semaphores, but never kills `_liveProcesses` (ffsubsync/ffmpeg) and never awaits `_laneTasks`. `_extractWake` is not disposed either, while `_wakePump` is. `_disposing` is a plain `bool` read from pump/lane threads.
- Evidence: `_disposing = true; try { _cleanupTimer.Dispose(); } catch … try { _wakePump.Release(); } catch … try { _wakePump.Dispose(); }`
- Why it matters: after a server shutdown/plugin reload, orphaned ffmpeg/ffsubsync processes keep reading the media shares with no owner.
- Direction for a fix: terminate tracked processes, signal the lanes to stop and dispose both semaphores, using a volatile/shared shutdown token.

### 15. Logging while holding the queue lock
- Area: scheduler
- Where: SubSyncService.cs:1056-1065 (`CancelBatch`)
- Severity: medium
- What is wrong: the queued-jobs loop writes a log line per cancelled job inside `lock (_queueLock)`. `_logger` here is Jellyfin's file/console logger, so a slow log sink blocks the lock the enqueue path and the planner both need — the class of thing AGENTS.md explicitly forbids.
- Evidence: `lock (_queueLock) { foreach (…) { job.Status = …; _logger.LogInformation("Cancelled queued job {JobId} of batch {BatchId}", …); } }`
- Why it matters: cancelling a large batch on a busy/slow-logging server freezes queueing for as long as the writes take.
- Direction for a fix: collect the ids under the lock and log after it.

### 16. `KillAll` busy-waits with `Thread.Sleep` and fabricates its return count
- Area: scheduler
- Where: SubSyncService.cs:1152-1157 and 1176
- Severity: medium
- What is wrong: the call blocks its (request) thread up to 3 s in a `Thread.Sleep(100)` polling loop. The returned tuple then reports `processesKilled > 0 ? Math.Max(processesKilled, runningKilled) : runningKilled` — a synthesised number that mixes "CTS cancelled" with "process tree killed", so the API reports kills that were never verified.
- Evidence: `while (DateTime.UtcNow < deadline && _liveProcesses.Values.Any(p => !SafeHasExited(p))) { Thread.Sleep(100); }`
- Why it matters: the Kill button can take seconds to respond (on a Jellyfin request thread), and the reported count can exceed what actually died.
- Direction for a fix: poll asynchronously, and return the measured counters separately.

### 17. Completed jobs are evicted whenever the store exceeds 50 entries
- Area: caching
- Where: SubSyncService.cs:3909-3911
- Severity: medium
- What is wrong: the age condition is OR-ed with `_jobs.Count > 50`, so a batch of more than 50 subtitles loses its Completed entries (and their `_jobContexts`) on the next cleanup tick regardless of age. `SweepLibraryAsync` counts `result.Completed` from that same live list, and `HasCompletedSync` reads it too.
- Evidence: `.Where(kvp => kvp.Value.Status != SyncJobStatus.Completed || (kvp.Value.FinishedAtUtc is not null && kvp.Value.FinishedAtUtc < cutoff) || (_jobs.Count > 50))`
- Why it matters: History loses rows mid-batch, the sweep's "N ok" total under-reports, and "already synced" markers disappear for a large run.
- Direction for a fix: keep the eviction purely time-based (or age-relative to batch completion).

### 18. Five near-identical process runners, two argument styles
- Area: other (duplication)
- Where: SubSyncService.cs:4514 (`RunProcessArgumentListAsync`), 4570 (`RunCapturedAsync`), 4622 (`RunProcessAsync`), 4686 (`RunProcessWithStderrCallbackAsync`), 4764 (`RunProcessCaptureAsync`)
- Severity: medium
- What is wrong: the five share the same start/redirect/register/kill/wait body with drifting details. `RunProcessArgumentListAsync` and `RunProcessWithStderrCallbackAsync` use `ArgumentList`, while `RunProcessAsync`, `RunCapturedAsync` and `RunProcessCaptureAsync` still build a hand-escaped `Arguments` string (contradicting the project's own "all process invocations use ArgumentList" rule) and pass `EscapeArg`'s **bash**-style quoting into .NET's **Windows**-style parser.
- Evidence: `process.StartInfo.ArgumentList.Add(argument);` (4529) vs `Arguments = arguments,` (4577) and `return $"\"{arg.Replace("\"", "\\\"")}\"";` (4866).
- Why it matters: a path with quotes/unicode breaks the venv/install path on Windows and on any non-trivial filename; every future fix has to be applied five times.
- Direction for a fix: collapse to one runner taking a token, an `IReadOnlyList<string>` and an optional per-line callback.

### 19. `out_time_ms` is converted as milliseconds
- Area: extraction
- Where: SubSyncService.cs:4430-4434
- Severity: medium
- What is wrong: ffmpeg's `-progress` key `out_time_ms` is emitted in **microseconds** (a long-standing ffmpeg quirk). This branch divides by 1000, so on a build that does not emit `out_time_us` the computed fraction is ~1000× too large, is clamped to 1.0, and the progress bar jumps straight to 20%.
- Evidence: `if (trimmed.StartsWith("out_time_ms=", …) && long.TryParse(trimmed[12..], …, out var millis)) { return millis / 1000.0; }`
- Why it matters: on those ffmpeg builds the user sees the extraction "finish" instantly and then nothing until it really finishes. I did not run ffmpeg here, so the microsecond claim is from the documented behaviour, not from a local measurement.
- Direction for a fix: treat `out_time_ms` as microseconds (or drop it and rely on `out_time_us`).

### 20. A cancelled extraction is reported as a failure and takes the fallback path
- Area: extraction
- Where: MkvSubtitleExtractor.cs:303-316 (catch-all) with the cancellation returns at 641-646 / 729-733; consumer at SubSyncService.cs:4266
- Severity: medium
- What is wrong: `OperationCanceledException` thrown inside `Prefetch`'s `Parallel.For` is caught by the generic `catch (Exception ex)` and turned into `reason = "OperationCanceledException: …"`, `Method = "failed"`, `return false`. The caller cannot tell "killed by the user" from "malformed container": it logs `extract fallback to ffmpeg: reasons=matroska-index: OperationCanceledException…` and proceeds into the ffmpeg path.
- Evidence: `reason = ex.GetType().Name + ": " + ex.Message; stats.Method = "failed";`
- Why it matters: a kill produces a misleading log and a pointless fallback, and the diagnostics that matter (which reader refused, and why) are buried under a cancellation string.
- Direction for a fix: rethrow cancellation from `TryExtract` and let the caller treat it as such.

### 21. Prefetch faults lose the real error inside an `AggregateException`
- Area: extraction
- Where: MkvSubtitleExtractor.cs:2616-2644 with the catch at 303
- Severity: medium
- What is wrong: `RandomAccess.Read` failures inside `Parallel.For` surface as `AggregateException`; the handler stringifies only `ex.Message`, so "The network path was not found" / "Permission denied" is reduced to whatever the aggregate's message carries, and the inner exception type — the thing that distinguishes a dead share from a locked file — is discarded before anything is logged.
- Evidence: `catch (Exception ex) { Diag(ex.ToString()); reason = ex.GetType().Name + ": " + ex.Message; … }`
- Why it matters: the single most common real-world failure (the share went away) produces an unhelpful reason and a slow ffmpeg retry.
- Direction for a fix: unwrap `AggregateException` and keep the first inner exception's type and message in `reason`.

### 22. `MeasureSyncChange` is computed twice per job
- Area: ffsubsync
- Where: SubSyncService.cs:3445 and 3621 (with `DescribeSyncChange` → `MeasureSyncChange`)
- Severity: medium
- What is wrong: the same measurement (two full `File.ReadLines` passes plus a least-squares fit) is run once before writing to decide acceptance, and again afterwards to produce the History text, on different file pairs (input vs temp, then backup/input vs output). Two code paths that must agree about the same numbers.
- Evidence: `var measured = MeasureSyncChange(subtitleInputPath, tempOutput);` … `job.Outcome = DescribeSyncChange(outcomeInput, job.OutputPath);`
- Why it matters: an extra full read of both subtitles per job on the share, and the History text can disagree with the decision that was made from the first measurement.
- Direction for a fix: measure once and derive the outcome text from the same struct.

### 23. `ClearStaleJobDirectories` recursively deletes anything under the scratch root
- Area: other (write path)
- Where: SubSyncService.cs:1358-1392
- Severity: medium
- What is wrong: it enumerates `TempPath` and `Directory.Delete(directory, recursive: true)` for everything whose name is not `"ref"` and not a job id currently in `_jobs`. The protection is a two-name allow-list; anything else that ever lands in `<CachePath>/subsync` (a new sub-cache, a lock file directory, a manually placed folder) is removed without confirmation.
- Evidence: `if (name.Equals("ref", StringComparison.OrdinalIgnoreCase) || _jobs.ContainsKey(name)) { continue; }` then `Directory.Delete(directory, recursive: true);`
- Why it matters: a "clear cache" click can delete data that is not the plugin's scratch output. Today the directory layout happens to hold only `ref` and job ids — I verified `SpeechCache`/`SubtitleCache` live under `StatePath`, not here — so this is a latent hazard rather than an active bug.
- Direction for a fix: invert the check — only delete names that parse as a job id.

### 24. Cue deduplication uses a hash as the set key
- Area: extraction
- Where: MkvSubtitleExtractor.cs:636
- Severity: low
- What is wrong: `seen` is a `HashSet<long>` holding `position * 31 + cueRef.RelativePosition`, not the pair itself, so two distinct (cluster, offset) pairs can collide and the second block is silently skipped.
- Evidence: `|| !seen.Add(position * 31 + cueRef.RelativePosition))`
- Why it matters: a dropped cue is a missing line in the output. Collisions need two clusters within ~10 KB of each other with offsets differing by 31× that gap, which I could not construct for realistic files — flagging it as a defect in form (hash-as-identity) rather than a demonstrated data loss.
- Direction for a fix: key the set on the tuple, or dedupe on the cue time.

### 25. Short reads are accepted as truncated cue text
- Area: extraction
- Where: MkvSubtitleExtractor.cs:1577-1585
- Severity: low
- What is wrong: if `ReadNear` returns fewer bytes than the block's declared payload, the payload is trimmed to what was read and the resulting partial text is still turned into a cue. On a share that returns short reads under load (or on a truncated file) this writes a chopped subtitle line.
- Evidence: `if (payloadRead < payloadLength) { payload = payload.AsSpan(0, payloadRead).ToArray(); }`
- Why it matters: silently clipped lines in the synced subtitle, indistinguishable from real content.
- Direction for a fix: retry the read, or treat a short payload as "block unreadable" and fall back.

### 26. Culture-sensitive parsing/formatting in two places
- Area: other
- Where: SubSyncService.cs:2819-2831 (`ParseSrtCueStarts`) and 2568 (`SweepLibraryAsync`)
- Severity: low
- What is wrong: `int.TryParse(parts[0], out var h)` (hours/minutes/seconds and the fraction digits) uses the current culture rather than `CultureInfo.InvariantCulture`, unlike the rest of the file; a server locale with native digit shapes (e.g. `ar-SA`) can fail or mis-parse these. `$"Library sweep — {DateTime.Now:yyyy-MM-dd HH:mm}"` likewise formats with the current culture and calendar, so a Thai or Buddhist-calendar locale labels the batch with a different year.
- Evidence: `if (int.TryParse(parts[0], out var h) && int.TryParse(parts[1], out var m) && int.TryParse(parts[2], out var s))`
- Why it matters: every offset measurement (and therefore the accept/refuse decision) is computed from these numbers; a mis-parse makes a real shift read as "no change" and skips writing a valid correction.
- Direction for a fix: pass `CultureInfo.InvariantCulture` to both parses and format the batch label invariantly.

### 27. `Diag` builds its message even when diagnostics are off, and writes to stderr
- Area: logging
- Where: MkvSubtitleExtractor.cs:185-191 with call sites 439, 443, 459, 465, 540, 545, 554, 596-597, 618, 1364, 1436, 1738
- Severity: low
- What is wrong: `Diag(string)` receives an already-interpolated string, so every call site formats (and at 596 runs a LINQ `Count(r => r. RelativePosition >= 0)` over all cue refs) regardless of `VerboseDiagnostics`; only the write is conditional. The output goes to `Console.Error.WriteLine("[mkv] …")` rather than `PluginLog`, so it is not in the file the user is told to hand over.
- Evidence: `private static void Diag(string message) { if (VerboseDiagnostics) { Console.Error.WriteLine("[mkv] " + message); } }`
- Why it matters: needless work in the parse hot path, and the diagnostics that would explain a bad extraction never reach the plugin log.
- Direction for a fix: guard at the call site (or take a format/lambda) and route through `PluginLog`.

### 28. Magic numbers that should be settings, and one that contradicts the documented policy
- Area: extraction / ffsubsync
- Where: MkvSubtitleExtractor.cs:1605 (`start + 2000`), 2371 (`+ 7000` / `+ 1500`), 2975 (`< 12` cues); SubSyncService.cs:3502 (`> 10000`), 2904/2916 (`Math.Max(…, 60) * 1000L * 20` / `* 2`), 3484 (`ceilingMs - 500`)

The 10 s reference threshold is described by the project's own AGENTS.md as the setting `MaxSubtitleReferenceOffsetSeconds` (default 30 s) with a refusal, not a note — that setting does not exist anywhere in the repo, and the code only adds a note.

- Why it matters: behaviour that the docs describe as configurable/refusing is neither; users cannot tune it, and the two multipliers (20× with framerate correction on, 2× off) are asymmetric in a way nothing explains.
- Direction for a fix: promote the thresholds to `PluginConfiguration` (or delete the AGENTS.md claim) and name the constants.

### 29. Non-volatile `_disposing`, unsynchronised `_lastPassFinishedUtc`
- Area: scheduler
- Where: SubSyncService.cs:261, 302 (written at 1600, read at 2296)
- Severity: low
- What is wrong: `_disposing` is a plain bool read in the pump and lane loops from other threads (no barrier), and `_lastPassFinishedUtc` is a plain `DateTime` written by lane threads and read by the pump without any synchronisation. A torn/stale read of the DateTime is impossible in practice on 64-bit, but the missing barrier means the pump can see a stale timestamp.

- Direction for a fix: `volatile` the flag and use `Interlocked`/`Ticks` for the timestamp.

### 30. `DescribeExtraction`'s catch-all relabels anything unknown as ffmpeg

- Severity: low

- Direction for a fix: fall back to the method string itself rather than an ffmpeg claim.

### Part B — Findings

### F1. `POST /SubSync/Install` lets any authenticated user run apt-get/pip as root
- Area: api
- Where: `Api/SubSyncController.cs:320-339` (`InstallFfSubSync`) → `Services/SubSyncService.cs` `InstallFfSubSyncAsync` / `EnsurePythonAvailableAsync`
- Severity: critical
- What is wrong: The endpoint has no elevation requirement — class-level `[Authorize]` only, and no `RequiresElevation` policy exists anywhere in the plugin. It runs `python3 -m venv`, `pip install --upgrade pip`, `pip install ffsubsync "setuptools<81"` and, when python3 is missing, `apt-get update` plus `apt-get install -y python3 python3-venv`. With the bundled binary present the UI disables the button, but the endpoint stays callable and still does all of that work for no benefit.
- Evidence:
```csharp

var (installExit, installOutput) = await RunProcessCaptureAsync(
    "apt-get", "install -y --no-install-recommends python3 python3-venv", null)
```
- Why it matters: A non-admin user (or anyone with a valid token) can trigger package installation and arbitrary pip installs inside the Jellyfin container — a privilege-escalation path reachable from a plain HTTP request, and an easy way to break the server.
- Direction for a fix: Require Jellyfin's admin/elevation policy on this endpoint (and on the other server-wide ones), and return early with a clear message when the bundled binary is present so nothing is installed.

### F2. `POST /SubSync/Kill` is global, id-less and unowned
- Area: api
- Where: `Api/SubSyncController.cs:401-414` → `SubSyncService.KillAll()`
- Severity: high
- What is wrong: The request carries no job or batch id; `KillAll()` cancels every `Queued` job in `_runOrder` (all batches, all users) and kills every live ffsubsync/ffmpeg process. ### F3. Item-scoped endpoints have no per-item access check (IDOR, read and write)

### F28. Error shapes are inconsistent, so the UI shows whatever came back
